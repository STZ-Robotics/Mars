# Simulation bridge

Translates between gz-transport (the engine), HALSim WebSocket (the robot
code) and NT4 (the app). The contract is in
[`sim/protocol/`](../protocol/README.md).

**Status:** telemetry and the `vendor` profile's hardware loop work and are
verified, including the swerve with position control in the engine. The whole
`hal` profile (HALSim WebSocket) is still missing.

## Building and running

It needs the `mars-sim` conda environment for the C++ libraries:

```
conda activate mars-sim
$env:PKG_CONFIG_PATH = "$env:CONDA_PREFIX\Library\lib\pkgconfig"
cargo build --bins
```

Or `..\verify.ps1`, which builds everything and runs the verification layers.

```
mars-sim-server worlds/testbot.sdf run
mars-bridge --robot-map models/testbot/robot-map.json
```

## Binaries

| Binary | What for |
|---|---|
| `mars-bridge` | The bridge. Telemetry to NT4 and, in the `vendor` profile, the hardware loop with the robot code. |

| `fake-robot.py` | Plays the robot code: publishes duty, reads the state and verifies the circle closed. |

### Why the app's NT4 client is not reused

`desktop/src-tauri/src/nt4/client.rs` is a CONSUMER client with Tauri woven
through its whole reconnection loop: it emits five events to the frontend and
takes its instance from `state::<NT4State>()`. Decoupling it would mean
refactoring code that works, with a risk of regressions in the app.

**This decision was already revisited**, when the `vendor` profile arrived --
which does need to subscribe, and was the noted trigger. It stood: adding
prefix subscription to this client was ~60 lines, while taking Tauri out of
the other one's reconnection loop is still a risky refactor that leaves
nothing better.

## Verification

`nt-probe.py` brings up an NT4 server with **WPILib's `ntcore`**, the
reference implementation -- the same one that runs on a roboRIO. That is
deliberate: a test written by us could share the bridge's misunderstanding of
the wire format, and ntcore cannot. It acts as the server because in
simulation that role belongs to the robot code.

```
pip install pyntcore
python nt-probe.py [seconds] [min_travel_m]
```

With `min_travel_m` it also requires the pose to FOLLOW the robot, and it has
to be driven in parallel. Without it, a static pose cannot tell "the bridge
works" from "the bridge published once and got stuck".

## Why the FFI and not pure Rust

Both crates that speak gz-transport from Rust were evaluated. **`gz-transport`
0.10 (an FFI wrapper around the C++) was chosen** after the pure path turned
out to be unworkable.

`gz-transport-rs` 0.1.0 is a pure reimplementation of the protocol,
attractive because it avoids linking against C++. Reading works perfectly.
**Publishing does not**: it advertises its *bind* address instead of a
destination one.

```
C++  /mars/state/pose      ->  tcp://10.48.71.132:57408
Rust /mars/cmd/actuators   ->  tcp://0.0.0.0:57416     <-- not connectable
```

`0.0.0.0` means "any interface" to whoever binds, but it is not a valid
destination: the C++ subscriber tries to connect and fails without emitting
any error. The engine never receives commands even though `gz-topics` shows
the topic advertised with the right type.

The bug is in `src/transport/publisher.rs`, which does
`socket.bind("tcp://0.0.0.0:0")` and advertises the result as is. The crate
itself already does it right for service sockets, with
`get_local_ip_for_endpoint(endpoint, host_ip)` in `src/transport/service.rs`,
which also honors `GZ_IP`. `Publisher::bind` does not use it and does not even
receive the `Config`, so **`GZ_IP` does not work as a workaround**. It is worth
reporting upstream: the fix is one line.

The original argument against the FFI --- not linking against conda's libs ---
turned out not to hold: the engine forces shipping the conda environment
anyway, so linking adds no new runtime dependency.

### What was ruled out along the way

Each one cost a full round; they are here so nobody repeats them:

- **It was not the partition.** Both sides compute `hostname:username` the
  same, and with a fixed `GZ_PARTITION` the problem gets worse (reading breaks
  too).
- **It was not discovery time.** With 12 seconds of waiting the same thing
  happens.
- **It was not that the advertisement did not go out.** A third node saw
  `/mars/cmd/actuators [gz.msgs.Actuators]` perfectly.
- **It was not the plugin.** With `MARS_VERBOSE=3` the engine confirmed
  `[MarsLink] protocol 0.1.0, 4 actuators` and published its state without
  trouble.

## The library name shim

Besides generating the protocol, `build.rs` creates library aliases.
conda-forge's `.pc` files are written with the Unix convention and ask for
`-lprotobuf` and `-lzmq`, counting on the linker to prepend `lib`. MSVC does
not: it looks for a literal `protobuf.lib`, while the installed file is
`libprotobuf.lib`.

The `cargo:rustc-link-lib=` lines are emitted by `gz-transport-sys` and cannot
be removed, so `build.rs` gives it what it asks for: a hard link with the
right name in `OUT_DIR`. If a new `LNK1181` shows up, add the name to the
`ALIASES` list and that is it.

## The engine closes the position loop

Each actuator declares its control mode in the SDF's `<actuator>`:

| mode | reads from `gz.msgs.Actuators` | who closes the loop |
|---|---|---|
| `duty` | `normalized` (-1..1) | nobody; applied as is |
| `position` | `position` (joint radians) | **the engine**, with a PD at the physics rate |

Position mode is not a convenience: it is the only way to simulate a CAN motor
faithfully. A TalonFX closes its loop **inside** the controller, at ~1 kHz,
and the robot code only sends it the setpoint.

A swerve forces it. Holding the steering from the robot code, with duty, was
tried first and it does not work: a 12.8:1 MK4 steering stage with a Kraken
has ~90 N·m across ~0.008 kg·m² of reflected inertia, i.e. 10 700 rad/s². In
the 20 ms of a robot cycle that is 214 rad/s. It was tried at 50 Hz (269° of
deviation) and at 250 Hz (145°): faster helps, but the problem is not the
period — it is that no loop over the network has authority over something that
fast.

With the loop in the engine, the same swerve holds its steering within
**0.6°** while accelerating flat out, and follows a 34° setpoint with 1–2.5° of
error.

That residual error comes from a PD with no integral term, and it is
expected. A real TalonFX removes it with feedforward (`kS`). If it ever gets in
the way, the way out is adding `ki` or a static friction term to the actuator,
not raising `kp`.

### The gains

`kp` and `kd` are attributes of the `<actuator>`, in duty per radian and per
rad/s **of the joint**. The swerve's come from sizing the steering: with
0.008 kg·m² of inertia and 90 N·m of authority, `kp=0.08` gives a natural
frequency of ~30 rad/s. `kd` adds to the joint's `<damping>`, which already
contributes its share.

The derivative comes from the **measured** velocity, not from differentiating
the error. Numerically differentiating an error that arrives over the network
amplifies any jump in the setpoint.

## Two modelling gaps the swerve uncovered

Both apply to any geared mechanism, not only swerve.

**Reflected rotor inertia.** `MarsLink` multiplies the TORQUE by the
reduction, but the INERTIA the motor presents to the joint goes with the
reduction SQUARED (`J_ref = J_rotor · n²`). Since the engine cannot touch the
ECS's inertias, it has to come from the model. Without it, a 12.8:1 steering
gets 90 N·m across 0.0015 kg·m² and the solver diverges on the first step:
the robot flies off at 5 000 000 rad/s. `gen_swerve.py` adds it.

**The tensor has to stay valid.** Adding the reflected inertia only to the
joint's axis violates the triangle inequality (each principal moment ≤ the sum
of the other two) and Gazebo rejects the world with `Error Code 19: invalid
inertia`. The perpendicular ones have to go up too. And with margin: at 5
decimals the rounding itself violates it again.
